## #129 Add Ladder workouts with rep progression, optional cap and saved results

## Outcome
Add Ladder as NextRound's sixth macOS workout mode, alongside EMOM, AMRAP, Countdown, Intervals and For Time. This is the main feature proposed for 1.8.0; planning only, not started.

## Proposed first-version design
- An ordered, nonempty list of catalog or Custom exercises. This first version uses repetitions: all movements use the same generated rep target for each rung. Respect supported units; explain why seconds-only movements cannot be selected. Do not silently convert holds, distance or calories to reps. Mixed-unit/per-exercise ladders are deferred.
- Ascending: starting reps + positive increment + rung count (2,4,6,8,10).
- Descending: starting reps - positive decrement + rung count (10,8,6,4,2). Reject any progression reaching zero or negative targets.
- Pyramid: starting reps + positive increment + rungs to peak, then mirror without duplicating the peak (start2/step2/peak rung3 =>2,4,6,4,2). One peak rung is a one-rung workout.
- Preview every rung, its targets and the planned total reps before Start/Save. Keep a long preview scrollable. Validate integer bounds and total generated workload consistently across TypeScript/Rust; document the selected limits and do not silently truncate.
- Optional time cap, existing lead-in/warning controls. Main clock counts active elapsed time, excluding lead-in/pauses; show cap remaining when enabled.
- User marks each movement complete to advance through the rung, with Undo before final resolution. Keep the active movement visible and controls reachable with keyboard and at 760×620.
- Completing the last prescribed movement opens a paused Finish confirmation; cancellation permits correction. Final confirmation records completed. Reaching the cap records timeCapReached and exact partial progression. No early-success result: Stop follows existing cancelled/discard semantics.
- Freeze progression while busy, in lead-in, in confirmation, or terminal. Finish/cap/Stop races produce one terminal result/cue; cap wins if already elapsed. Avoid a partial-rep editor in v1: record fully completed movements/rungs and planned next target, clearly distinct from measured reps.
- Existing start/warning/completion cue and display-sleep behavior apply; emit a cue once per rung transition and one final completion sound, not a replay burst after wake. No automatic rest or timed exercise advancement.

## Acceptance
- [ ] Sixth labeled home card, independent draft and setup route, preview and accessible progression controls.
- [ ] Deterministic shared/native semantics and regression tests for each pattern, invalid/large bounds, undo across rung boundaries, cap/manual-finish races, pause/Stop/Finish, sleep/wake and exactly-once cues/results.
- [ ] Preserve Ladder definition and performed progress in templates/history; Repeat loads an editable fresh draft without starting it. No changes to historical snapshots or the existing 103 catalog entries.
- [ ] Suggestions, equipment/focus/search and Custom choices work with Ladder's reps eligibility and explain empty results.
- [ ] Native session remains the authoritative clock; resolve how progress and terminal intent cross the existing adapter without introducing a second timer or lost-result reload path.
- [ ] Verify all six modes, minimum-window/keyboard flows, offline use, failed save/retry and backward-compatible storage, including unknown future data preservation.

## Product decisions
This issue records the proposed release design. No extra exercise seeding, new backend, automatic exercise sensing, intensity prescriptions or iOS work is included.

Part of 1.8.0 epic #128. Planning only; no implementation has started.


## #130 Allow updating an existing saved workout without creating duplicates

## Backlog slice
Scoped 1.8.0 work from #17 (saved workout library). Current source offers Load/Rename/Delete, while Save workout always creates a new copy. Editing a loaded routine has no explicit update-existing path. This is a usability gap, not a claim of corrupted data.

## Acceptance
- [ ] Loading a saved workout retains explicit source identity separately from the editable draft, including Ladder.
- [ ] Offer clear Update saved workout and Save as new actions with an explicit target name; never overwrite merely because names match.
- [ ] Persist the edited configuration/name atomically while preserving template ID; successful feedback refers to the exact saved draft and clears after further edits.
- [ ] Re-read and handle deleted or externally changed source templates without silently recreating/overwriting them. Keep the draft and offer explicit recovery.
- [ ] Cancel/load-replacement/route changes cannot accidentally update a different template; failed writes preserve both existing saved data and the draft.
- [ ] Past results remain immutable; test persistence, double-submit/failure/retry, source deletion/change and all six workout modes.

#17 remains the broader roadmap issue; loads/scaling and other unsatisfied acceptance are not declared complete by this slice. Planning only.

Part of 1.8.0 epic #128. Planning only; no implementation has started.


## #131 Add workout-mode and exercise search filters to history

## Backlog slice
Scoped 1.8.0 work from #19. Current history renders all results sorted by date with no search or mode filters. Six workout modes and a larger catalog make finding a prior session harder.

## Acceptance
- [ ] Filter by All or one of the six modes; search performed exercise names and descriptions in saved snapshots, including Custom entries. Case/whitespace normalization matches existing app conventions.
- [ ] Combine mode AND text filters without altering the underlying results; maintain chronological ordering and stable result identity.
- [ ] Clearly distinguish no saved history from no matching results; provide nearby clear-filter controls.
- [ ] View/repeat/delete address the correct result while filtered; deletion updates the filtered list and exercise-usage queries correctly.
- [ ] Preserve useful filter context after opening/closing detail and safe repeat cancellation. Filtering is local and offline, with accessible labels and minimum-window coverage.
- [ ] Test all six modes, legacy snapshots, Custom text, empty results and deletion under active filters.

No personal bests, unlike-workout rankings, load comparison, or inferred performance scores. Full repeat-performance comparison and notes remain in #19/#18. Planning only.

## #132 Fix setup validation leaking between workout modes

## Source-inspected risk
At 1.7.0, state/workout.ts has a single shared errors map, and all five setup routes render that map. Editing a field clears the entire map. Routes have independent drafts but no corresponding per-mode validation ownership. Confirm the visible reproduction before changing behavior.

## Reproduction to lock down
Submit an invalid Countdown duration, navigate home and open a valid AMRAP/For Time setup, then inspect messages/aria-invalid. Also submit multiple invalid fields and edit only one: unrelated invalid fields should not misleadingly appear resolved.

## Acceptance
- [ ] Add failing regressions proving the applicable cross-mode/stale-validation paths.
- [ ] Scope setup validation to the relevant draft/mode; navigation or edits in another mode do not mislabel a valid draft.
- [ ] Clear/revalidate the edited field and dependent duration/progression fields without hiding unrelated outstanding errors.
- [ ] Start and Save validate the full current config; loading/repeating a valid config clears the appropriate old errors.
- [ ] Preserve unrelated runtime, read, storage and control errors; do not use blanket error clearing.
- [ ] Cover existing five modes and Ladder, including cap toggles and invalid progression preview.

Planning for 1.8.0; source inspection, not yet a browser-reproduced report. If reproduction disproves it, record evidence and narrow/close the issue rather than manufacturing a fix.

Part of 1.8.0 epic #128. Planning only; no implementation has started.


## #133 Fix setup error announcements and focus on invalid inputs

## Source-inspected gap
Most timing fields set aria-invalid without linking the specific error text. Countdown/AMRAP/For Time/Intervals render a detached list of errors, while EMOM links only its duration field. Invalid Start does not consistently direct keyboard users to the field requiring correction.

## Acceptance
- [ ] Give field errors stable unique IDs and connect them with aria-describedby while retaining existing help text. Combined duration errors describe both minute/second inputs appropriately.
- [ ] On explicit invalid Start/Save submission, focus and scroll the first relevant invalid control into view; do not steal focus on every keystroke or background update.
- [ ] Explain exercise-list errors next to the list and focus an appropriate reachable control; include Ladder progression validation.
- [ ] Avoid duplicate/conflicting live-region announcements; ensure errors remain understandable beyond color alone.
- [ ] Verify keyboard behavior and minimum-window layouts across six modes with focused DOM/browser regressions; record actual VoiceOver observations separately when physical access is available.

Coordinate with mode-scoped validation; do not broadly redesign setup. Planning only; confirm the source-inspected gap during implementation.

## #13 Define exercise taxonomy, intensity scales, and initial content policy

## Outcome

Resolve the remaining product definitions for the full exercise and workout libraries.

## Release scope

**Post-0.1.0 backlog.** Outside the macOS EMOM release tracked in https://github.com/StormKiln/NextRound/issues/1.

## Acceptance criteria

- [ ] Define equipment identifiers, exercise type categories, and intensity vocabulary with examples.
- [ ] Distinguish exercise effort descriptors, prescribed workout intensity, and actual user-perceived effort; account for load/pace/rest.
- [ ] Decide curated versus user-created library content and document provenance/licensing for bundled descriptions.
- [ ] Define duration estimates versus fixed time caps and how these feed recommendation constraints.

## Dependencies

- https://github.com/StormKiln/NextRound/issues/3

## Planning notes

Source: the NextRound product brief in README.md and the requested EMOM flow. Items explicitly marked proposed are implementation defaults to validate, not additional user-confirmed requirements. Existing splash/icon artwork is complete; reuse it instead of recreating it.

## 1.8.0 scope — #128
Selected as supporting definition/content work for Ladder and future library features. Inventory the existing 103-entry equipment/type/focus vocabulary and aliases; preserve catalog IDs, stored snapshots and picker behavior. Document current curated content plus workout-local Custom entries, original-description provenance and the future editable-library boundary. Define intensity as a contextual descriptor, distinct from prescribed effort and user-reported effort, without claiming a movement has one personalized intensity. Explicitly distinguish elapsed results, fixed timers, caps and uncertain duration estimates: a Ladder rep count is not a guaranteed completion duration. Provide concrete examples and identify any migration-requiring taxonomy change as a separate decision, not an implicit rename. No new recommendation algorithm or catalog-editor feature is included. Planning only.
